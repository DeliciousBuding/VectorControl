# 架构决策记录（ADR）

更新时间：2026-02-07

本文档用于沉淀高影响架构取舍，避免口头共识丢失。每条记录建议保持“背景-决策-后果”三段。

## ADR-001：不做黑盒行情预测，优先规则可解释

- 背景：项目定位为个人决策中枢，核心诉求是可审计与可回放，而非短期预测准确率竞赛。
- 决策：策略层输出基于阈值与风控规则的 `advice/action_plan`，不引入不可解释黑盒模型作为主决策引擎。
- 后果：
  - 优点：建议可追溯、易复盘、可在面试中清晰解释。
  - 代价：无法宣称“预测能力”，更多依赖纪律执行与风险控制。

## ADR-002：交易事实采用 `pending/confirmed` 双态

- 背景：基金交易“先下单后确认”是常态，单状态模型会导致收益口径与真实清算错位。
- 决策：交易流水强制支持 `pending/confirmed`，并通过 `/api/transactions/sync_pending` 完成补全。
- 后果：
  - 优点：收益计算口径清晰，状态可解释，避免误导。
  - 代价：实现复杂度上升，需要补全逻辑与审计字段。

## ADR-003：手工导入优先 YAML，而非先做 OCR

- 背景：当前阶段目标是稳定闭环与可控成本，不是追求输入自动化炫技。
- 决策：优先建设 `transactions_import.yaml` 规范与幂等导入接口，OCR 作为后续可选增强。
- 后果：
  - 优点：实现快、可调试、可回放，便于错误定位。
  - 代价：导入前需要人工整理结构化文本。

## ADR-004：状态解释能力作为发布门槛

- 背景：投资决策场景下“数据来自哪里、截至何时、是否确认”是第一优先信息。
- 决策：核心接口统一返回 `data_status`，核心页面必须提供状态说明入口；无状态解释能力的功能不发布到 `main`。
- 后果：
  - 优点：降低误判风险，提升系统可信度与工程成熟度。
  - 代价：接口与前端联动改造成本增加，需要持续维护一致性。
