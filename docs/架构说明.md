# VectorControl 架构说明（A/B/C + X）

更新时间：2026-02-08 12:25:53

本文档是当前版本的主架构说明，目标是让系统在持续扩展时保持“专业、冷静、理性的决策中枢”风格，不再出现功能散落和职责混写。

## 1. 架构目标

- 事实数据可追溯：持仓、交易、净值、动作、设置都有明确真源和审计轨迹。
- 决策口径可解释：建议来自规则与风险，不来自不可解释黑盒。
- 执行闭环可回放：从建议到执行到复盘可串联。
- 前端信息架构稳定：总览常驻、风险前置、基金详情独立页面。
- 部署与运维可观测：线上故障可快速定位，不出现“按钮点了只报 Not Found 但无上下文”。

## 2. 总体结构（A/B/C 三系统 + X 跨层治理）

```text
               +----------------------------------------+
               | X 跨层治理（鉴权/审计/可观测/发布门禁） |
               +-------------------+--------------------+
                                   |
  A 数据与事实层  ----------->  B 决策与规则层  ----------->  C 执行与复盘层
 (Fact Layer)                (Decision Layer)             (Execution Layer)
```

- A 只负责“事实正确且可演进”。
- B 只负责“把事实转成建议与指令”。
- C 只负责“执行闭环与呈现体验”。
- X 负责横切能力，防止安全、观测、发布规范散落到业务代码中。

## 3. A 系统：数据与事实层（Fact Layer）

### 3.1 A1 数据源适配器（Connectors）

数据入口统一进入适配层，不允许前端直接写“爬取逻辑”。

- 手动导入：YAML/JSON（继续保留）。
- 交易导入规范：统一使用 `transactions_import.yaml`（v1），强制包含时间语义与幂等键，避免“导入同单多次入账”。
  - 单一事实来源：`docs/交易流水YAML导入规范.md`
- 基金公共数据连接器：抓取基金主数据、最新净值、历史净值。
- 飞书文档知识连接器：用于飞书机器人能力建设，只允许白名单域名（如 `open.feishu.cn`），禁止无约束全网抓取。
- 连接器必须具备：超时、重试、频控、失败隔离、源标识（source）。

### 3.2 A2 事实真源（DB Truth）

运行真源统一为数据库（本地 SQLite / 生产 PostgreSQL），YAML 仅做导入导出。

现有核心表（保留）：

- `holdings`
- `actions_log`
- `estimate_snapshot`
- `user_accounts`、`user_sessions`
- `user_settings`、`user_profiles`
- `fund_catalog`
- `fund_profit_confirm`

新增规划表（增量演进，不破坏现有接口）：

- `fund_master`：基金主数据（基金代码、全称、简称、市场、状态、来源更新时间）。
- `fund_alias`：基金别名与检索词（如“纳指”“纳斯达克100”）。
- `fund_nav_daily`：基金净值时序（日级，含单位净值、累计净值、净值日期、来源）。
- `fund_source_job`：抓取任务与状态（运行时间、成功数、失败数、错误摘要）。
- `fund_source_job_log`：抓取任务明细日志（基金维度状态、重试次数、失败原因、来源与时间）。
- `fund_transactions`：交易流水（买入/赎回/定投/转换），支持 `occurred_at` 精确时间、`status`（`pending/confirmed`）。
- `audit_logs`：关键字段变更审计（谁在何时改了什么）。

### 3.3 A3 数据补全与对账（Resolvers）

解决“先发生、后确认”的资金场景，避免业务层直接写补丁逻辑。

- `pending -> confirmed` 补全流程（交易确认后反写）。
- 按净值数据推导确认份额与金额（标记 `computed` 来源）。
- 幂等去重（业务主键 + 指纹）。
- 数据质量校验（时间逆序、净值缺口、异常波动标记）。

## 4. B 系统：决策与规则层（Decision Layer）

### 4.1 B1 估值与口径（Estimator）

- 单基金估值与组合聚合。
- 失败降级：单基金抓取失败不阻断全局结果。
- 支持快照缓存与增量刷新，减少全量重算。
- 已落地：估值链路支持“短 TTL 快照命中 + 基金级增量报价复用”，并输出 `incremental_reused_quotes / incremental_fetched_quotes` 用于观测。

### 4.2 B2 风控与覆盖（Risk）

- 覆盖率、集中度、敞口、回撤风险统一口径。
- 风险摘要可直接提供给前端“风险状态条”。

### 4.3 B3 策略与建议（Policy/Advice）

- 基于阈值规则生成“可执行动作”而非行情预测。
- 输出结构化建议：`advice` + `action_plan`。

### 4.4 B4 状态解释器（Status Explainability）

- 统一输出 `data_status` 元数据（`status/asof/note`），用于解释页面当前口径是 `confirmed/estimating/partial`。
- B 层负责把 A 层事实状态转成用户可读语义，避免前端自行猜测数据新鲜度与可信度。
- 当存在 `pending` 交易、数据源失败或覆盖率不足时，必须在 `note` 中给出可读说明。
- 周末休市口径规则：`cn_hk/us_overseas` 组在周末按“最近结算快照”展示，前端状态不再误报“盘中估算”。

## 5. C 系统：执行与复盘层（Execution Layer）

### 5.1 C1 执行记录（Actions/Transactions）

- 记录计划动作与实际执行动作。
- 交易与赎回必须支持“具体发生时间”（`occurred_at`）。
- 支持后续审计回放（变更链路与责任归属）。

### 5.2 C2 复盘与报告（Report）

- 日报/周报把“事实 + 建议 + 执行结果”串联成闭环。
- 支持飞书机器人推送与失败重试。

### 5.3 C3 前端工作台（UI）

前端信息架构按“总览 -> 选择 -> 深入”组织：

- 首页：核心状态与主动作。
- 持仓页：事实快照与列表操作。
- 基金页（新增一级入口）：基金数据库搜索与浏览。
- 基金详情页（独立路由，非持仓内联）：`/funds/:fund_id`。
- 交易页：流水管理（`pending/confirmed` 分区）。
- 复盘页：报告与执行回顾。
- 系统状态页（新增运维入口）：`/system/status`，仅展示系统健康与任务状态，不承载业务交易操作。

关键交互要求：

- 持仓区上方前置“风险状态条”。
- 已落地：风险状态条展示集中度/回撤预估/结构预警摘要，并支持跳转到风险中枢详情区。
- 明确区分 `Estimating` 与 `Confirmed` 状态。
- 已落地：收益图默认显示 `0%` 基准虚线，净值参考图显示成本线虚线，列表 Mini-Sparkline 显示时间范围标签。
- 新增基金时支持模糊搜索补全（输入“纳指”可列出候选基金并可点击查看详情）。
- 核心页面必须提供“数据状态说明”入口（Tooltip 或状态卡），可追溯当前口径、更新时间、异常说明。
- 已落地：登录/刷新/设置/交易链路统一错误映射，失败提示包含“下一步”建议，避免“点了没反应”。
- 基金详情图表区必须联动 `data_status`（`status/asof/note`），禁止仅展示静态图表标题而不说明当前口径。
- 交易页必须展示生命周期三段（`pending -> confirmed -> 计入收益`）并高亮当前节点，避免“状态不可追踪”。

## 6. 基金数据库 API 设计（目标契约）

### 6.1 查询类接口

- `GET /api/funds/search?q=纳指&limit=10`
  - 返回主数据 + 别名命中信息，支持代码/名称/拼音/简称/别名。
- `GET /api/funds/{fund_id}`
  - 返回基金主档案（名称、代码、分类、状态、最近更新时间）。
- `GET /api/funds/{fund_id}/nav/latest`
  - 返回最新净值及来源（第一阶段：估值快照优先 + 实时抓取回退）。
- `GET /api/funds/{fund_id}/nav/history?from=YYYY-MM-DD&to=YYYY-MM-DD`
  - 返回历史净值序列与完整性标记（第一阶段来源为估值快照）。

### 6.2 同步与运维接口

- `POST /api/funds/sync`（管理员）
  - 触发主数据与净值同步任务（支持 `async_mode` 后台执行）。
- `GET /api/funds/sync/jobs/{job_id}`
  - 查看抓取任务状态与错误摘要（`running/done/partial/failed` + 细粒度失败分类日志）。

### 6.3 交易时间与补全接口

- `GET /api/transactions`
  - 返回交易流水与 `summary`（`total/pending/confirmed/last_occurred_at`），支持 `fund_id` 维度过滤，并附带 `data_status`。
- `POST /api/transactions/import_yaml`
  - 按 `transactions_import.yaml` 导入交易，返回 `added/skipped/conflicted` 统计并默认写入 `pending`。
  - 导入字段与冲突策略以 `docs/交易流水YAML导入规范.md` 为准。
- `POST /api/transactions`
  - 入参必须支持 `occurred_at`（精确到分钟/秒）。
- `PATCH /api/transactions/{id}`
  - 支持修正发生时间、状态、净值、份额等关键字段。
  - 已落地：每次有效修正写入 `audit_logs`（`entity_type=fund_transaction`），用于审计回放。
- `POST /api/transactions/sync_pending`
  - 触发 `pending -> confirmed` 对账补全。
  - 第一阶段已落地：按 `fund_nav_daily` 净值补全 `nav/shares/confirmed_at` 并回写 `data_status`，支持按 `fund_id` 单基金对账。

### 6.4 系统状态与统一口径接口

- `GET /api/system/status`
  - 返回运行版本、Git commit、数据源健康、最近同步任务、最近 pending 对账时间。
- `data_status`（推荐嵌入核心响应）：
  - `status`: `confirmed | estimating | partial`
  - `asof`: 数据口径时间
  - `note`: 可读解释（例如“含 1 笔 pending 交易”）

## 7. 飞书机器人能力边界（增强版）

- 消息推送：建议、日报、风险告警。
- 消息通道统一抽象：`notifier` 层统一分发 `feishu/telegram`，Telegram 当前为默认关闭的预留通道，占位实现不发起真实网络请求。
- 文档学习：允许联网抓取飞书开发文档，但必须走受控连接器。
- 安全边界：
  - 白名单域名抓取。
  - 记录抓取日志与来源 URL。
  - 明确缓存与过期策略，避免重复抓取。
  - 禁止将密钥写入日志或前端。

## 8. 运维与可观测（含测速工具）

测速工具链路基线：

- 前端调用：`/api/settings/network-benchmark/latest`、`/api/settings/network-benchmark/run`
- 后端路由：`backend/app/api/routers/settings.py`
- 后端测速探针支持“站点级协议/端口”与 TLS EOF 场景的 HTTP 回退，避免把所有站点强制按 `https:443` 误判失败。

线上出现“Not Found”时按以下顺序排查：

1. 后端镜像版本是否包含上述路由。
2. Nginx `/api` 反向代理是否正确转发到 backend。
3. 前端版本是否与后端路由版本匹配。
4. Gate-D 验收脚本是否包含测速接口健康检查。

目标：把“测速可用性”纳入发布门禁，避免回归。

## 9. 约束与演进策略

- 代码新增功能必须先归类到 A/B/C/X，再决定落地位置。
- 契约演进只增不删，避免前端回归风险。
- 优先做 A 系统最小闭环（基金数据库与交易事实完整），再放大 B/C。
- 文档、ROADMAP、代码三者同批同步，保持单一事实来源。
- 状态可解释性优先于功能扩张：新增页面若无法说明数据口径与更新时间，则不进入发布分支。
- `main` 发布前必须执行文档全量巡检（`README.md`、`ROADMAP.md`、`docs/架构说明.md`、`docs/开发规范.md`、`docs/接口契约.md`、`docs/交易流水YAML导入规范.md`、`docs/P0线上故障排查SOP.md`、`docs/状态解释验收样例.md`、`docs/最新进度.md`、`docs/Git工作流.md`、`docs/部署与运行.md`），并在发布说明写明文档更新结论。
- `main` 发布前执行 `python scripts/check_docs_gate.py` 作为文档门禁自动化检查。
- `main` 发布前推荐统一执行 `python scripts/check_release_preflight.py`，将文档门禁与构建检查串成单次预检。
- `check_docs_gate.py` 需同时校验核心文档、发布模板、文档范围一致性以及 `.githooks/*`、`.github/workflows/*` 关键门禁文件完整性。
- push 前通过 `.githooks/pre-push` 自动执行 `python scripts/check_docs_gate.py --strict`。
- 状态解释回归样例以 `docs/状态解释验收样例.md` 为基线，Gate-D 留档模板需包含对应截图与结果。
- PR 到 `dev/main` 由 `.github/workflows/docs-gate.yml` 执行云端门禁（`--strict --diff-base`）。
- 远端分支保护通过 `python scripts/branch_protection.py` 固化并定期复检，避免门禁规则被手工漂移（当前敏捷阶段后置治理）。
- 发布提交信息通过 `.githooks/commit-msg` 执行 `python scripts/check_release_message.py` 自动校验版本号与四段说明。
- 发布提交的 `文档:` 段必须包含“检查范围 / 更新结论 / 延后项（无则写无）”，缺一即门禁失败。
- `main` 发布后通过 `python scripts/check_main_release.py` + `.github/workflows/release-consistency.yml` 校验 Tag 与发布说明一致性。
- 当前单人敏捷阶段可将“分支保护远端治理”后置处理，不阻塞当轮业务闭环；相关回补任务统一放入 `ROADMAP.md` 的持续改进区。
